# Техническое задание

## Архитектура

- Сервер — FastAPI, JSON API с префиксом `/api/v1`. Актуальный выбор фронтенда указан в [решениях](00-decisions.md).
- Предлагаемая база — PostgreSQL, SQLAlchemy и миграции Alembic. Одна база для профилей, расписания, успеваемости, объявлений, сессий и заявок. Фронтенд получает рабочие данные по API.
- Развёртывание с одним публичным origin для интерфейса и API. Для локальной разработки фронтенд может проксировать API. Инструкции запуска, миграций и заполнения демоданными должны быть воспроизводимыми с чистого клона.
- Публичная сборка использует HTTPS, постоянное хранилище и серверные переменные окружения. Выбор хостинга остаётся за командой. Публичная проверка из России без VPN входит в релизную приёмку.
- Пустой репозиторий допускает предложенную структуру `backend/`, `frontend/`, `docs/`. Если проект уже существует, сначала прочитать его инструкции и сохранить пригодные соглашения.

## Модель данных

| Сущность | Минимальные данные и связи |
|---|---|
| Пользователь, сессия | Уникальный логин, хеш пароля, роль, признак активности. У сессии — владелец, срок действия и возможность отзыва. |
| Факультет, группа, профиль | Группа относится к факультету. Профиль содержит пользователя, ФИО, направление, курс и группу. У сотрудника отдельно задан обслуживаемый факультет. Проверять согласованность этих связей. |
| Занятие | Группа, дисциплина, преподаватель, начало и конец, корпус, аудитория, состояние. Изменение хранит прежнее и актуальное значение и отметку времени. |
| Учебный результат | Студент, дисциплина, семестр, вид контроля, статус, дата контроля, оценка или отметка «Зачтено» при наличии результата. |
| Объявление | Заголовок, текст, автор или источник, аудитория вуз / факультет / группа, дата публикации, необязательный срок показа, признак закрепления, необязательная связь с занятием. |
| Заявка, история, сообщение | Уникальный номер, студент, тип, статус, дата подачи, ориентир срока, способ получения. В истории — событие, время и автор. Вопрос и ответ относятся к конкретной заявке. |
| Демонстрационный документ | Привязка к заявке. Готовый PDF с пометкой «Демонстрационный образец», доступный через защищённый маршрут. Можно генерировать по запросу из вымышленных данных. |
| Уведомление | Получатель, тип, заголовок, ссылка на связанный объект, дата, признак прочтения. Общие новости берутся из адресных объявлений. |

## Черновик API

Пути ориентировочные. Агент должен согласовать контракт между фронтендом и сервером и описать фактические пути в документации.

| Область | Маршруты |
|---|---|
| Сессия и профиль | `POST /auth/login`, `POST /auth/logout`, `GET /me` |
| Учёба | `GET /schedule` с диапазоном дат, `GET /schedule/{id}`, `GET /academic-results` с фильтром семестра |
| Объявления и уведомления | `GET /announcements`, `GET /announcements/{id}`, `GET /notifications`, `PATCH /notifications/{id}` |
| Студенческие заявки | `GET /requests`, `POST /requests`, `GET /requests/{id}`, `GET /requests/{id}/document`, `POST /requests/{id}/reply` |
| Кабинет сотрудника | `GET /staff/requests`, `GET /staff/requests/{id}`, `POST /staff/requests/{id}/transitions`, `GET /staff/announcements`, `POST /staff/announcements` для создания и `PATCH /staff/announcements/{id}` для правки и смены состояния, `GET /staff/schedule`, `PATCH /staff/schedule/{id}` |

## Правила доступа и переходов

- Для браузера предусмотреть серверные сессии. Cookie сессии в публичной сборке устанавливается с HttpOnly, Secure и подходящим SameSite. Для изменяющих запросов обеспечить серверную проверку CSRF, включая согласованное поведение входа и выхода. Выход отзывает сессию. Пароли хешировать с Argon2id через поддерживаемую библиотеку.
- Проверять роль, принадлежность и аудиторию на сервере при каждом обращении. Студент получает профиль, оценки и заявки по своему идентификатору из сессии. Расписание ограничено его группой. Сотрудник видит заявки только своего факультета. Те же проверки действуют для вложений, отдельных страниц объявлений, уведомлений и связанных объектов.
- Сотрудник управляет объявлениями, адресованными его факультету и его группам. Состояния объявления — черновик, опубликовано и снято с публикации. Студент получает только действующие опубликованные записи. Общевузовские объявления можно загрузить демокомандой. Признак аудитории и ссылки проверяются по серверным данным.
- Разрешённый путь заявки — «Принята» → «В работе» → «Готова». Путь с уточнением — «В работе» → «Нужно уточнение» → «В работе» после ответа. Только сотрудник берёт в работу и завершает. Студент отвечает только на свою заявку в состоянии ожидания уточнения.
- Смена статуса, запись истории и уведомление должны сохраняться согласованно. Повторное или параллельное действие не создаёт второй переход и лишнее уведомление. Скачивание доступно при статусе «Готова» и проверке владельца. Ошибка отправки отображается на фронтенде с возможностью повторить действие.
- Секреты, рабочие пароли и строки подключения поступают из окружения. В репозитории — шаблон `.env.example`. Демопароли для жюри передаются отдельно в комментарии к работе. У тестовых учётных записей нет лишних прав.

- Правка расписания требует принадлежности занятия факультету сотрудника. Хранить прежние и новые значения. Отмена оставляет запись доступной студенту со статусом «Отменено». При отображении связанной карточки подтягивать актуальные поля занятия, чтобы не показывать устаревшую аудиторию как действующую.

## Демоданные

Наполнить два факультета и две группы. У двух студенческих аккаунтов разные профили, занятия, оценки и история заявок. Оба видят одно общее объявление. У каждого есть своё факультетское сообщение, у первой группы — связанный перенос 305 → 412, у второго студента другая пара. Для живого показа добавить отдельную консультацию с исходной аудиторией 305, которую сотрудник ещё не переносил. Даты демонаполнения ориентировать на день запуска демонабора или на настраиваемую дату сценария, чтобы «Сегодня» можно было проверить при показе. Подготовить обычную неделю и день без занятий.

Команда заполнения работает повторно без размножения начальных записей. Сброс выделяется в отдельную команду, которую запускает команда в контролируемой среде. Сборка жюри сохраняет пользовательские действия после перезапуска.
